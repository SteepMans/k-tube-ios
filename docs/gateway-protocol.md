# Протокол прокси-шлюза

K-Tube не ходит на YouTube напрямую. Каждое соединение с хостом YouTube или Google открывается на внешнем
прокси-шлюзе по ключу пользователя, а шлюз сам соединяется с сайтом. Адрес шлюза задаёт сборка
(`KTUBE_GATEWAY_URL`) или пользователь вместе с ключом.

## Открытие соединения

TLS до шлюза на порт 443 (ALPN `http/1.1`), затем:

```
GET /v1/proxy HTTP/1.1
Host: <шлюз>
Connection: Upgrade
Upgrade: tcp/1
Authorization: Bearer <ключ>
X-TGeshka-Client: streamtube-ios/<версия>
X-Proxy-Target: www.youtube.com:443
```

Имя заголовка с клиентом — часть протокола шлюза, его ждёт сервер.

Ответ `101 Switching Protocols` — дальше по соединению идут сырые байты до цели (внутри обычный TLS с сайтом).

| Ответ | Значение |
|---|---|
| 403 | хост не входит в список разрешённых |
| 404 | ключ не принят |
| 429 | у ключа слишком много открытых соединений |
| 502 | шлюз не смог найти или открыть цель |
| 503 + `X-Proxy-Error: no_leg` | у шлюза сейчас нет выхода к сайтам |

`GET /v1/info` с тем же ключом отвечает JSON; поле `proxy` говорит, разрешён ли ключу этот режим.

## Как это устроено в приложении

- `URLSession` приложения настроен на локальный прокси `127.0.0.1:<порт>`: каждый `CONNECT host:443`
  превращается в соединение через шлюз.
- AVPlayer получает видео с того же локального сервера: мастер-плейлист HLS, плейлисты дорожек и сегменты
  он скачивает через шлюз и переписывает ссылки на себя.
- Список разрешённых хостов: `Core/Sources/KTubeCore/Gateway.swift`.
